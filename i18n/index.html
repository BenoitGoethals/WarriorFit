    Internationalization (i18n)¶

    How WarriorFit renders its UI in multiple languages, per browser session, with live switching and no page reload.

    Supported languages: English (en), Dutch (nl), French (fr). Default / fallback language: English.

    1. The big picture¶

    ┌─────────────────────────────────────────────────────────────────────┐
│  translations/{en,nl,fr}.json   ──flat key → string lookup tables    │
└───────────────┬─────────────────────────────────────────────────────┘
                │ loaded & cached on first use
                ▼
        translator.t(key)  ──────────────► returns string for current language
                │  asks "what language?"        │ falls back: lang → en → key
                ▼                               │
        LanguageStore.get_language()            │
                │  reads a per-session          │
                │  reactive.Value               │
                ▼                               ▼
   session._wf_language_rv (reactive.Value[str])
                ▲
                │ set_language(lang)
                │
   app_server.py  ── language switcher (dropdown) fires reactive Effects
                  ── bumps `lang_version` / `nav_version` → navbar re-renders

    The design has three moving parts:

    Part File Responsibility
    Translation tables warriorfit/i18n/translations/*.json The actual strings, keyed by dotted IDs
    Translator warriorfit/i18n/translator.py t(key) lookup + caching + fallback
    Language store warriorfit/i18n/language_store.py Per-session current language, backed by a Shiny reactive.Value

    The public API is re-exported from the package root:

    from warriorfit.i18n import t, LanguageStore, SUPPORTED_LANGS

    2. Translation files¶

    warriorfit/i18n/translations/en.json, nl.json, fr.json.

    Each file is a flat JSON object mapping a dotted string key to the translated text. Keys are namespaced by area (nav., settings., common., progress., …):

    {
  "nav.welcome": "Welcome",
  "nav.my_progress": "My Progress",
  "settings.title": "Settings",
  "common.close_btn": "Close"
}

    Rules:

    • All three files must contain the same keys. (Currently 469 keys each.) A key present in en.json but missing elsewhere will silently fall back to English.
    • Keys are stable identifiers — never translate or rename them, only their values.
    • The dotted namespace is a convention for readability; the lookup itself is a plain flat dict get (no nesting is parsed).

    3. The translator — t(key)¶

    warriorfit/i18n/translator.py

    def t(key: str) -> str:
    lang = LanguageStore.get_language()          # current session language
    value = _load(lang).get(key)                 # try requested language
    if value is None and lang != "en":
        value = _load("en").get(key)             # fall back to English
    return value if value is not None else key   # finally, the bare key

    Two things to note:

    1. Caching. _load(lang) reads {lang}.json from disk once and memoizes it in a module-level _cache dict. Subsequent calls are pure dict lookups. The cache lives for the process lifetime, so editing a JSON file requires a restart (or --reload).

    2. Three-level fallback — never throws, never returns None:

    3. requested language → English → the raw key string.
    4. A missing translation degrades gracefully to English, and a completely unknown key surfaces as itself (e.g. t("nav.bogus") → "nav.bogus"), which makes gaps visible in the UI rather than crashing.

    Usage is uniform across every page:

    from warriorfit.i18n import t

ui.h2(t("settings.title"))
ui.input_action_button("mp_refresh_btn", t("common.refresh"))
return t("progress.not_logged_in")   # also works in server-side render functions

    4. The language store — per-session state with reactivity¶

    warriorfit/i18n/language_store.py

    This is the clever part that makes live language switching work without a reload.

    _SESSION_LANG_ATTR = "_wf_language_rv"
_DEFAULT_LANG = "en"
SUPPORTED_LANGS = ("en", "nl", "fr")

class LanguageStore:
    @classmethod
    def _get_rv(cls) -> "reactive.Value[str] | None":
        session = get_current_session()
        if session is None:
            return None
        rv = getattr(session, _SESSION_LANG_ATTR, None)
        if rv is None:
            rv = reactive.Value(_DEFAULT_LANG)        # lazily created, once per session
            setattr(session, _SESSION_LANG_ATTR, rv)
        return rv

    @classmethod
    def get_language(cls) -> str:
        rv = cls._get_rv()
        return _DEFAULT_LANG if rv is None else rv.get()   # ← reactive read

    @classmethod
    def set_language(cls, lang: str) -> None:
        if lang not in SUPPORTED_LANGS:
            lang = _DEFAULT_LANG                       # validate / coerce
        rv = cls._get_rv()
        if rv is not None:
            rv.set(lang)                              # ← reactive write

    Key properties:

    • Per session, not global. The current language is stored as an attribute (_wf_language_rv) on the Shiny session object. Two users connected at the same time each have their own language — there is no shared global state.

    • Backed by a reactive.Value. Because get_language() calls rv.get(), any Shiny reactive context that calls t() (and therefore get_language()) automatically registers a dependency on the language value. When set_language() calls rv.set(), Shiny re-invalidates and re-runs those contexts. This is what propagates a language change to the UI.

    • Safe outside a session. If there is no current session (e.g. module import time, or unit tests), get_current_session() returns None and the store returns the default en rather than failing.

    • Input validation. set_language() rejects anything outside SUPPORTED_LANGS and silently coerces to the default — callers can pass raw input safely.

    5. The switching flow (end to end)¶

    The wiring lives in warriorfit/ui/app_server.py.

    5.1 The switcher control¶

    _lang_switcher() builds a small <select> dropdown in the navbar, pre-selected to the current language:

    ui.input_select(
    "lang_select",
    label=None,
    choices={"en": "EN", "nl": "NL", "fr": "FR"},
    selected=LanguageStore.get_language(),
    width="auto",
)

    It is appended to the navbar in _build_navbar() (nav_items.append(_lang_switcher())). There are also lang_en / lang_nl / lang_fr action-button handlers wired for an optional button-style switcher.

    5.2 Reacting to a selection¶

    def _change_lang(lang: str) -> None:
    LanguageStore.set_language(lang)              # 1. update session language
    lang_version.set(lang_version.get() + 1)     # 2. bump version counters …
    nav_version.set(nav_version.get() + 1)       #    … to force dependent re-renders

@reactive.Effect
@reactive.event(input.lang_select)
def _set_lang_from_select() -> None:
    lang = input.lang_select()
    if lang and lang != LanguageStore.get_language():
        _change_lang(lang)

    5.3 Re-rendering the UI¶

    main_content_container is a @render.ui output that rebuilds the navbar. It reads nav_version.get(), so bumping that counter forces a full rebuild of the navbar — and because _build_navbar() calls every page's ui_factory() (which call t(...)), the whole menu and page UIs are regenerated in the new language:

    @render.ui
def main_content_container() -> Any:
    ...
    else:
        _ = nav_version.get()      # depend on the counter
        return _build_navbar()     # rebuilds menus + page UIs via t()

    lang_version is used similarly by other reactive contexts that need to rebuild on a language change (for example the login dialog: _ = lang_version.get()).

    So there are two complementary mechanisms that cause the UI to update:

    1. Implicit (reactive): Any @render.* function that calls t() automatically depends on the language reactive.Value and re-runs on change.
    2. Explicit (version bump): UI that is built imperatively (the navbar, page ui_factory() output) is forced to rebuild by incrementing nav_version / lang_version, which those @render.ui blocks depend on.

    5.4 Sequence diagram¶

    User picks "FR" in dropdown
   │
   ▼
input.lang_select fires
   │
   ▼
_set_lang_from_select()  ──► _change_lang("fr")
   │                              │
   │                              ├─► LanguageStore.set_language("fr")
   │                              │        └─► session._wf_language_rv.set("fr")  (invalidates deps)
   │                              ├─► lang_version += 1
   │                              └─► nav_version += 1
   ▼
Shiny re-runs invalidated reactive contexts
   │
   ├─► main_content_container() re-renders  ──► _build_navbar() ──► page.ui_factory() ──► t("...")  → French
   └─► any @render.* using t()              ──► t("...")  → French
   │
   ▼
Browser DOM updated — no page reload

    6. How to use it as a developer¶

    Display a translated string¶

    from warriorfit.i18n import t

ui.h2(t("reports.title"))

    This works both in UI factory code (page layout) and inside server-side render functions (@render.text, @render.ui, etc.). In a render function it additionally becomes reactive to language changes for free.

    Add a new string¶

    1. Add the same key to all three files: en.json, nl.json, fr.json.
    2. Use a sensible dotted namespace (area.thing), matching the page/area it belongs to.
    3. Reference it with t("area.thing").
    4. Restart the app (the JSON cache is loaded once per process).

    Add a new language¶

    1. Add the ISO code to SUPPORTED_LANGS in language_store.py.
    2. Create translations/<code>.json with every key translated (copy en.json as a template).
    3. Add the option to the choices dict in _lang_switcher() in app_server.py.

    7. Gotchas & invariants¶

    • Keep the three JSON files key-synchronized. A divergent key set means silent English fallback. (A quick check: each file currently has 469 keys.)
    • JSON is cached for the process lifetime. Editing a translation requires an app restart, or run with shiny run ... --reload.
    • Language is session-scoped and in-memory only. It is not persisted to the DB or a cookie — a new browser session starts again at the default (en).
    • t() outside a session returns the default language. Fine for tests and import time; just be aware module-level constants evaluated at import are effectively English.
    • Unknown keys render as the key itself — handy for spotting missing translations in the running UI.

    8. File reference¶

    File Purpose
    warriorfit/i18n/__init__.py Public exports: t, LanguageStore, SUPPORTED_LANGS
    warriorfit/i18n/translator.py t(key) lookup, disk loading + caching, fallback chain
    warriorfit/i18n/language_store.py Per-session reactive current-language store
    warriorfit/i18n/translations/en.json English strings (also the fallback table)
    warriorfit/i18n/translations/nl.json Dutch strings
    warriorfit/i18n/translations/fr.json French strings
    warriorfit/ui/app_server.py _lang_switcher(), switch handlers, navbar re-render
